# Spike A-04 — Supported-App Catalog

**Question.** Does the curated catalog work without `QUERY_ALL_PACKAGES`?

**Decision.** `GO`. Installed catalog applications are detected with their real name and icon through twelve targeted `<package>` declarations. The merged manifest carries no broad visibility permission and the application requests no runtime permission at all.

Executed as plan phase 03.

## The catalog

`shared/supported-app-catalog/catalog.json`, schema version 1, ten entries: Instagram, TikTok, YouTube, Facebook, X, Reddit, Snapchat, Telegram, Discord, VK.

```json
{
  "id": "tiktok",
  "displayName": "TikTok",
  "packageNames": ["com.zhiliaoapp.musically", "com.ss.android.ugc.trill"]
}
```

Three schema decisions, each answering something the phase raised:

1. **A stable `id`, separate from any package name.** Rules and stored selections reference the id, so a package rename does not orphan user data.
2. **`packageNames` is a list, not a string.** The phase risk table anticipated OEM and regional variants needing aliases. Rather than defer that to a later schema version, the first version carries it: TikTok already ships as two packages, and Telegram as two. The first alias found on the device wins, and that choice is unit tested.
3. **`displayName` is a fallback, not the source of truth.** When an application is installed, the label shown is what `PackageManager` reports, so the user sees the name their device uses. `displayName` is only for entries that are not installed and therefore have no device label.

The file lives in exactly one place. The Gradle module wires it in as an asset for the application and as a test resource for JVM tests, so the tests validate the file that actually ships rather than a copy.

### Resolution on the device

```
id=instagram state=NotInstalled     id=x         state=NotInstalled
id=tiktok    state=NotInstalled     id=reddit    state=NotInstalled
id=youtube   state=Installed        id=snapchat  state=NotInstalled
id=facebook  state=NotInstalled     id=telegram  state=NotInstalled
                                    id=discord   state=NotInstalled
                                    id=vk        state=NotInstalled
```

The screen reads "1 of 10 supported applications are installed on this device". YouTube shows its real launcher icon and the label `PackageManager` reports. Every other entry is a dashed placeholder, the sentence "Not installed on this device", and `N/A` — a normal explained state rather than an error or a disabled checkbox, which is what component 2c in `design/DESIGN_EXPORT_ANALYSIS.md` calls for.

### Installed and removed again

```
pm uninstall --user 0 com.google.android.youtube   → Success
                                                   → id=youtube state=NotInstalled
pm install-existing --user 0 com.google.android.youtube
                                                   → id=youtube state=Installed
```

No crash, no error state, no empty row. The transition is just a different state of the same entry.

### Nothing outside the catalog is visible

Chrome is installed on this emulator and is not in the catalog. It does not appear anywhere in the list, and the code has no path that enumerates installed applications: resolution only ever asks `PackageManager` about package names the catalog already names.

### Permissions actually requested

```
requested permissions:
  com.blocksocial.spike.a03.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION
install permissions:
  com.blocksocial.spike.a03.DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION: granted=true
```

The single entry is generated by androidx.core. It is a signature permission scoped to this package and grants nothing to any other application. There is no runtime permission and therefore no prompt.

## Automated checks

| Check | Result |
|---|---|
| `./gradlew :a03:assembleDebug` | `BUILD SUCCESSFUL` |
| `./gradlew :a03:test` | `SupportedAppCatalogParserTest tests=9 failures=0`, `CatalogResolverTest tests=6 failures=0` |
| `./gradlew :a03:lint` | `0 errors, 3 warnings` |
| Merged manifest | `absent: QUERY_ALL_PACKAGES`, `absent: SYSTEM_ALERT_WINDOW`, 12 targeted `<package>` declarations |

The parser tests run against the shipped `catalog.json` and assert the schema version, that all ten required applications are present, that every entry has an id, a display name and at least one package, and that aliases exist. They also assert the parser rejects an unsupported schema version, a missing `apps` array, an entry with no package, duplicate ids, and one package mapped to two entries — the last two being the failures that would silently corrupt a user's rules.

The resolver tests cover the installed case, the missing case, alias matching, alias precedence, catalog ordering, and that an installed application outside the catalog is never returned.

`org.json` was added as a **test-only** dependency. Android provides the same API at runtime; the JVM needs a real implementation for the parser tests the phase requires.

## Findings for production

1. **The catalog cannot be validated by reading it.** Duplicate ids and a package claimed by two entries both parse as valid JSON and both corrupt rule storage. Those checks belong in the build, not in a code review, which is why they are tests rather than documentation.
2. **`<queries>` and the catalog must not drift.** Twelve `<package>` lines currently mirror twelve package names by hand. A catalog entry added without a matching manifest line resolves to not-installed on every device, silently and with no error. Production should generate the manifest entries from `catalog.json` or add a test that fails when the two disagree.
3. **Catalog coverage is a product question, not a technical one.** Ten entries is what the phase asked for. Which applications testers actually want is a beta question, recorded in the phase 24 feedback set.

## Limits of this evidence

Only one catalog application exists on this emulator image, so name and icon rendering is proven for one real case and nine placeholders. Regional and OEM package variants are unverified: the schema supports aliases and the alias logic is unit tested, but no device in this project has ever presented a variant. That confirmation belongs to the beta.
